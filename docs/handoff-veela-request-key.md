# ส่งต่อ: เปิดกุญแจ request ให้ Veela (บอท LINE ของสวิตเชอร์)

> ถึง Claude Code ที่ดูแลคลังนี้ · จาก Minerva (ทีม PMDC ของปุ๊ก) · 2026-10-28
> ต่อจาก PR #21 (v1.276.0 · deploy แล้ว) · ops-log 28 ต.ค. เขียนว่า "ยังไม่ได้ออก key veela · รอนัทตอบปุ๊ก 2 เรื่อง" —
> ไฟล์นี้ตอบ 2 เรื่องนั้น (ในฐานะข้อเสนอ) และเสนอทางส่งกุญแจที่ไม่มีใครต้องถือค่ากุญแจข้ามฝั่ง

## สิ่งที่ขอ (เรียงตามลำดับ)

1. **รองรับรายการกุญแจแบบ hash** ใน `src/lib/mcp/auth.ts` (สเปกข้างล่าง) + เทสต์ → ออกเวอร์ชันตามปกติ
2. รอ Minerva คอมเมนต์ค่า `sha256:<hex>` ใน PR นี้ (ปุ๊กสร้างกุญแจบนเครื่องของเราเอง ค่าจริงอยู่ใน Keychain ฝั่งเราที่เดียว)
3. ตั้ง env ใน Portainer stack: `MCP_API_KEYS_REQUEST=veela:sha256:<hex>` → redeploy → จด ops-log
4. คอมเมนต์ใน PR ว่า deploy แล้วที่เวอร์ชันไหน — ฝั่งเราจะยิง `tools/list` ด้วยกุญแจจริงเพื่อตรวจว่าได้ scope `request` (8 tools) แล้วตอบกลับใน PR

ถ้าไม่อยากแตะโค้ด → ดู "ทางสำรอง" ท้ายไฟล์

## 1. สเปกกุญแจแบบ hash

เหตุผล: ตอนนี้ `parseKeyList` เก็บค่ากุญแจดิบใน env แล้ว `resolveBearerKey` เทียบตรง ⇒ ต้องมีคนถือค่าดิบข้ามจากฝั่งนี้ไปฝั่งเรา
(แชต/อีเมล/LINE = รั่วได้) · ถ้า env เก็บแค่ hash ฝั่งเราสร้างกุญแจเองแล้วส่งมาแค่ hash ซึ่งเปิดเผยได้ — ค่ากุญแจไม่เคยออกจากเครื่องเรา

- รูปแบบรายการ: `<label>:sha256:<64 hex ตัวเล็ก>` (เช่น `veela:sha256:3f…a9`) · รายการแบบเดิม `<label>:<key>` ยังใช้ได้เหมือนเดิมทุกประการ
- `parseKeyList`: ถ้าส่วนหลัง label ขึ้นต้น `sha256:` และตามด้วย hex 64 ตัว → เก็บเป็น `{ label, keySha256: <hex>, scope }`
  · ขึ้นต้น `sha256:` แต่ hex ไม่ครบ/ไม่ใช่ hex → **ทิ้งรายการนั้น** (ไม่ตกไปเป็นกุญแจดิบชื่อ `sha256:…`) และ log เตือน 1 บรรทัดโดยไม่พิมพ์ค่า
- `resolveBearerKey`: คำนวณ `sha256(token)` เป็น hex ครั้งเดียว แล้วเทียบกับรายการ hash ด้วย `timingSafeEqual` (ความยาวเท่ากันเสมอ = 64) ·
  รายการดิบเทียบแบบเดิม · ลำดับ "first match wins: read → request → full" คงเดิม
- `McpKey` ที่คืนไปให้ route ยังมี `label` และ `scope` เหมือนเดิม (audit `via: mcp:veela` ไม่เปลี่ยน)
- เทสต์ที่ควรมี (ต่อใน `src/lib/__tests__/mcp-readonly.test.ts` หรือไฟล์ใหม่):
  · hash ถูก → ได้ scope `request` + label `veela`
  · token ผิด → `null` · ส่ง hex เองเป็น token → `null` (ห้ามให้ hash ใช้แทนกุญแจได้)
  · `sha256:` ที่ hex สั้น/มีตัวพิมพ์ใหญ่ปน/ไม่ใช่ hex → ไม่เกิดกุญแจ และไม่ทำให้รายการอื่นในบรรทัดเดียวกันหาย
  · รายการดิบเดิมยังผ่านทุกเทสต์ที่มีอยู่
- อัปเดต `docs/mcp.md` + `.env.portainer.example` ให้บอกรูปแบบใหม่ (แนะนำให้กุญแจใหม่ทุกใบใช้แบบ hash)

ฝั่งเราสร้างกุญแจแบบนี้ (สุ่ม 32 ไบต์ · เก็บลง Keychain `hermes-switcher` / `VEELA_PROBOOK_KEY` · พิมพ์ออกแค่ hash):
`sha256` ของสตริงกุญแจตามที่ส่งใน header `Authorization: Bearer <key>` (ไม่รวมคำว่า Bearer · ไม่มีขึ้นบรรทัดใหม่ท้าย)

## 2. ค่าตั้งต้นของคำขอจากสวิตเชอร์ (ตอบคำถามข้อ 2 ของ PR #21 — เป็นข้อเสนอ รอปุ๊กยืนยัน)

| ช่อง | ข้อเสนอ | หมายเหตุ |
|---|---|---|
| programCode / ประเภทงาน | **ไม่ตั้งค่าตั้งต้น** — Veela ถามสวิตเชอร์ให้เลือกจากรายชื่อรายการ (program) ที่ดึงจาก tool อ่านที่มีอยู่ | เดาผิดรายการ = ใบเข้าผิดงาน แพงกว่าถามเพิ่ม 1 คำถาม |
| shootType | ขอให้บอกค่า enum ที่ใช้กับงานที่มีแค่สวิตเชอร์ (EVENT หรือค่าอื่น) | ฝั่งเราไม่รู้ enum จริง — ห้ามเดา |
| จำนวนกล้อง / ไมค์ | Veela ถามสวิตเชอร์ทุกครั้ง · ถ้าแอดมินมีค่าที่ใช้ประจำสำหรับงานสวิตเชอร์ ขอให้บอก จะใช้เป็นค่าเสนอในคำถาม | |
| switcherCount | 1 | |
| videographerCount | 0 | |

ระหว่างรอคำยืนยัน Veela อยู่โหมดซ้อม (ไม่ส่งใบจริง) ตามที่ตกลงใน PR #21 · ถ้า schema ของ `create_booking` ผ่านกุญแจ request
มีช่องบังคับอื่นนอกจากนี้ ขอให้ระบุไว้ในคอมเมนต์
