# Bug classes — รูปแบบความพังที่กลับมาซ้ำ

_v1.233.1 · 2026-09-23 · อ่านคู่กับ `docs/architecture.md` (ระบบทำงานยังไง) และ `docs/ops-log.md` (เกิดอะไรขึ้นวันไหน)_

หน้านี้ไม่ใช่ลิสต์บั๊ก แต่เป็น **รูปทรง** ของบั๊กที่ระบบนี้ผลิตซ้ำมาตลอดปี แต่ละคลาสมีอุบัติเหตุจริงกำกับ
พร้อมตัวเลข และชี้ไปที่ไฟล์/บรรทัดที่ "ตัวกัน" อยู่ตอนนี้ — เพราะรูปทรงเดียวกันจำง่ายกว่าเหตุการณ์ 50 เหตุการณ์

**วิธีใช้:** ก่อน merge อะไรก็ตามที่แตะ notification, worker, dry-run, สิทธิ์, หรือการลบของ
ให้ไล่ checklist ท้ายหน้า ถ้าโค้ดใหม่เข้าข่ายคลาสไหน ให้ไปอ่านคลาสนั้นก่อน
คอมเมนต์ในโค้ดของรีโปนี้มักบันทึกอุบัติเหตุที่ทำให้บรรทัดนั้นเกิดขึ้น — อ่านคอมเมนต์ อย่าอ่านแค่โค้ด

ทุกคลาสข้างล่างมีรากเดียวกัน: **สิ่งที่ระบบรายงาน ≠ สิ่งที่ระบบทำ ≠ สิ่งที่คนได้รับ**

## 1. `a record is not delivery` — แถวที่บอกว่า "ส่งแล้ว" ไม่ใช่อีเมลที่ถึงคน

ถ้าโค้ดบันทึก **เจตนา** แทน **ผล** ทุก metric ที่อ่านจากบันทึกนั้นจะโกหกตามกันหมด

**เกิดจริง (v1.186, 2026-08-21):** operator แจ้งว่าไม่ได้รับเมลแจ้งฟุตเทจมานาน ทั้งที่สัญญาณเขียวทุกตัว —
worker ติ๊กทุก 30 นาที, `errors=0`, SMTP ตอบ `235 Accepted`, และ audit 30 วันมี **85 แถวที่มี
`admin-digest` อยู่ใน `recipients` และ `emailError=null` ทุกแถว** ความจริงคือค่า boolean ที่
`notifyEmailDigest()` / `notifyDiscord()` คืนมา **ถูกทิ้งทั้งคู่** — `'admin-digest'` ถูกต่อเข้า
`recipients` จากตัวแปร "ตั้งใจจะส่ง" ล้วน ๆ และ Gmail ส่งเมลจากบัญชีหนึ่งไปหาบัญชีเดียวกันไม่ได้
(`EMAIL_FROM` = `REMINDER_ADMIN_EMAIL` = `SMTP_USER`) เมลจึงไม่เคยโผล่ทั้ง Inbox และ Sent

ก่อนหน้านั้น 5 สัปดาห์เป็นบั๊กพี่น้องกัน: `FOOTAGE_READY_AUDIENCE=admin` ทำให้ **103 การแจ้งเตือน**
เข้า digest ของ operator คนเดียว ไม่มีคนในกองได้รับสักใบ

**ทำแทน:** บันทึกเฉพาะช่องทางที่ฟังก์ชันส่งคืน `true` · แตกผลเป็นราย channel ห้ามยุบเป็น boolean เดียว
(v1.209.1 โดนซ้ำ: เก็บ `discord || lark` ลงฟิลด์ชื่อ `discord`) · แยก **liveness** (worker วิ่งไหม)
ออกจาก **delivery** (คนได้ยินไหม) เป็นคนละ endpoint เสมอ

**ดูโค้ด:** `src/lib/footage-ready.ts:429-441` (คอมเมนต์ WHY ของ `SentResult`) · `:469-471` และ
`:520-523` (`ADMIN_DIGEST` เข้ารายชื่อเฉพาะเมื่อส่งผ่านจริง) · `operatorChannels {digestOk, discordOk, larkOk}`

## 2. `error is not emptiness` — ความล้มเหลวที่หน้าตาเหมือน "ไม่มีข้อมูล"

`r.ok ? r.json() : []` แปลงทุก 502/401 ให้กลายเป็นลิสต์ว่าง แล้ว UI ก็พูดด้วยความมั่นใจว่า "ไม่มี"
ผู้ใช้จึงไม่มีเหตุผลให้กดใหม่

**เกิดจริง (v1.210, 2026-08-27):** `PP-26-039` ขึ้นว่า *"ไม่มี episode ที่ถ่ายได้"* ทั้งที่ของจริง
**มี 15 ตอน สถานะ Post-production จองได้ทุกตอน** (ยิง API ตัวเดียวกันผ่านเบราว์เซอร์ที่ผู้ใช้ล็อกอินอยู่
ได้ HTTP 200 · 15 episodes) ตัวจุดชนวนคือ Google เด้ง `unauthorized_client` เป็นระยะ
ที่เจ็บกว่าคือช่อง Project ID **มีแบนเนอร์เตือน** อยู่แล้วตั้งแต่แรก ส่วนช่อง Episodes ไม่มี — ทำไว้ครึ่งเดียว

น้องของมัน: **error ลบ affordance ไม่ใช่แค่ข้อมูล** — ปุ่ม "ส่งงาน" ทั้งบล็อกแขวนอยู่กับ
`{report && report.totalFiles > 0 && …}` ถ้าดึงรายงานไม่สำเร็จ `report` เป็น `null` ปุ่มก็หายไปทั้งปุ่ม
โดยไม่มีใครรู้ว่าเพราะอ่านไม่ได้

**ทำแทน:** ถามทุกครั้งว่า *"ถ้าพลาด ผู้ใช้จะเห็นอะไร"* ถ้าคำตอบคือหน้าตาเดียวกับ "ไม่มีข้อมูล" = UI กำลังโกหก ·
แยก state `error` ออกจาก `empty` + แบนเนอร์ + ปุ่มลองใหม่ · ฝั่ง server retry ครั้งเดียวด้วย token ใหม่

**ดูโค้ด (ตัวอย่างที่แก้แล้ว):** `src/app/_components/booking/BookingWizard.tsx:217` (`episodesError`) + แบนเนอร์ที่ `:1560`
**ยังเป็นแบบเดิมอยู่ (ของจริง ณ v1.233.1):** `RoutinePlanner.tsx:189` `{groups: []}` · `:270` `{items: []}` ·
`UploadSection.tsx:185,190` · `dashboard/[id]/page.tsx:109` (`ep-folders` ล้ม = ลิงก์ footage หายทั้งหน้า)

## 3. `empty is not delivered` — ว่าง ≠ ส่งงานแล้ว · อ่านไม่ได้ ≠ ไม่มี

การไม่เจอของ มีสองความหมายเสมอ: *มันไม่มี* กับ *เรามองไม่เห็น* โค้ดที่ยุบสองอันนี้เข้าด้วยกันจะลบของจริงทิ้ง

**เกิดจริง (2026-09-18, แก้ที่ v1.225):** `landing-lifecycle` ทิ้งโฟลเดอร์ drop ที่ "ว่าง + เลยกรอบ"
โดยตีความว่าว่าง = ฟุตเทจเข้ากล่องแล้ว วันนั้น IT ปิด NAS ฟุตเทจของ `POP-7TG-260916-01`
**ไม่เคยขึ้น Drive สักไฟล์** (พิสูจน์ได้จาก `modifiedTime == createdTime` เป๊ะทั้งสองโฟลเดอร์)
ระบบจึงทิ้งปลายทางที่ไฟล์ต้องลงทิ้งไป 10:27 น. และ `Booking.driveFolders.landing` ยังชี้ไปที่โฟลเดอร์ในถังขยะ

**เกิดจริงอีกรูป (v1.222):** `room-booking-reconcile` ใช้ `.catch(() => null)` เวลาอ่านระบบจองห้องกลางไม่ได้
แล้วล้าง `roomBookingNo` ทิ้ง — ห้องยังถูกยึดอยู่ฝั่งเขาแต่ไม่มีอะไรชี้กลับมาได้ และรอบถัดไปจะจองทับซ้อน
ในระบบที่ไม่มี idempotency (ตรวจ ส.ค.–ต.ค. แล้ว 67 ใบ รหัสไม่ซ้ำ = ยังไม่เกิดความเสียหายจริง)

พี่น้องอีกตัว: **ชื่อ + ขนาดตรงกัน ≠ ไฟล์เดียวกัน** — `TSS-WYS-260824-01` มี 585 ไฟล์ตรงกันทุกไฟล์
แต่ `DSC04216.ARW` ตัวใน landing เป็น Sony RAW จริง (`4949 2a00`) ส่วนตัวใน box เป็นหัว JPEG = เสีย
ถ้าลบตาม "ซ้ำ" จะเสียเฟรมนั้นถาวร **md5 เท่านั้นที่ตัดสินได้**

**ทำแทน:** ลบได้เฉพาะเมื่อ **รู้แน่** ว่าปลายทางมีของแล้ว · อ่านไม่ได้ = ไม่ทำอะไร + รายงานให้คน ·
โฟลเดอร์รก เสียแค่ความรก ส่วนการลบผิดจังหวะทำให้ไฟล์ไม่มีที่ลง

**ดูโค้ด:** `src/lib/landing-lifecycle.ts:205-220` (รอบ 19:00) และ `:368-376` (รอบเที่ยง) — ทั้งคู่เรียก

## 4. `no silent caps` — `take: limit` + ลำดับคงที่ = ท้ายคิวไม่มีวันถึง

เพดานที่อ่านเหมือน "ค่อยทำรอบหน้า" จะกลายเป็น "ไม่มีวันทำ" ทันทีที่ `orderBy` คงที่ทุกรอบ

**เกิดจริง (v1.185.2, 2026-08-21):** `reconcileCalendarGuests` ใช้
`orderBy: [{shootDate:'asc'}, {updatedAt:'desc'}]` + `take: limit` และ worker ส่ง `limit=50`
บนพรอดมี **62 ใบในขอบเขต** (0 ใบอยู่ในอดีต) แถวที่ 50 = 16 ก.ย. แถวที่ 51 = 22 ก.ย.
⇒ **งานวันที่ 22 ก.ย. – 11 ธ.ค. ไม่เคยถูก reconcile เลย** ปฏิทินเพี้ยนค้างได้ตลอดกาลโดยไม่มีใครรู้
Co-Producer เข้าปฏิทินได้ก็เพราะยิงมือด้วย `?limit=200`

**ทำแทน:** ถ้าต้องมีเพดาน ต้อง (ก) ตั้งธง `truncated` (ข) `console.warn` (ค) ให้ผลลัพธ์บอกออกมาว่าตรวจไม่ครบ ·
ถ้าไม่มีใครอ่านธงนั้น กลับไปอ่านคลาสที่ 7 · ทางที่ดีกว่าคือทำลำดับให้หมุน (เก่าสุดที่ยังไม่ตรวจก่อน)

**ดูโค้ด:** `src/lib/calendar-reconcile.ts:651-663` — คอมเมนต์ `NO SILENT CAPS` เขียนเหตุการณ์นี้ไว้ทั้งดุ้น ·
เทียบกับรายงานของ `footage-integrity` ที่เขียนบอกทุกครั้งที่ชนเพดาน 60 ใบ

## 6. `the check that can't fail` — ตัวตรวจที่ไม่มีทางฟ้อง

ตัวตรวจที่เทียบของกับตัวมันเอง / catch ที่ไม่มีวันทำงาน / เทสที่ข้ามเงียบ ๆ = ความมั่นใจฟรีที่ไม่มีของหนุน

**เกิดจริง (v1.222):**
- `roomChanged = want.roomId !== roomIdForLocation(b.locationId)` โดยที่ `want.roomId` ก็มาจาก
  `roomIdForLocation(b.locationId)` ตัวเดียวกัน ⇒ **เป็นเท็จเสมอ ไม่เคยจับอะไรได้เลย** และไม่มีบรรทัดไหน
  เทียบ *เวลา* เลย ผลคือแก้ใบจอง (เปลี่ยนห้อง/เลื่อนเวลา) แล้วห้องเดิมค้างที่ช่วงเดิมตลอดไป ช่วงใหม่ไม่มีห้อง
  และ `syncRoomBooking` ก็ไม่จองใหม่เพราะเห็นว่ามี `roomBookingNo` แล้ว — เงียบสนิททุกทาง
- `cancelRoomBookingFor` **ไม่ throw** (มันคืน `FORBIDDEN`/`UNKNOWN`) ⇒ `try/catch` ที่ใส่ไว้ใน
  hard delete **ไม่มีวันทำงาน** แถวจึงถูกลบพร้อม audit แถวสุดท้ายที่ยังบอกเลขจองห้องได้
- กฎ "กองนี้กินห้องช่วงไหน" เขียนสองที่: ตรวจว่างใช้ `call+4 ชม.` จองจริงใช้ `call+8 ชม.` = **เช็คแคบ จองกว้าง**
  และเคส `wrap == call` ฝั่งตรวจได้ช่วงเวลากลับหัว → `overlaps()` คืน false เสมอ = **"ว่าง 100%"**

**พี่น้องในฝั่งเทส (v1.204/205 และซ้ำอีกที v1.215):** เทสที่ขึ้นต้นด้วย `if (!existsSync) return`
จะ **ผ่านเงียบ ๆ** ตอนไฟล์ไม่อยู่ใน Docker build context — guard ตายไปแล้วโดยไม่มีใครรู้

**ทำแทน:** ตัวตรวจต้องเทียบกับ **ของจริงฝั่งนอก** เสมอ ไม่ใช่กับค่าที่เราคำนวณเอง ·
ตัวตรวจกับตัวส่งต้องเรียกฟังก์ชันเดียวกัน (ดูคลาสที่ 9) ·
เทสที่อาจข้าม ให้ใช้ `test(name, { skip: 'เหตุผล' }, fn)` ของ `node:test` ให้พิมพ์ `# SKIP` ออกมา
และพิสูจน์สามเคสเสมอ: **มีไฟล์ = ยังจับได้ · ไม่มีไฟล์ = ข้ามพร้อมเหตุผล · มีไฟล์ + ของผิด = ยังล้ม**

**ดูโค้ด:** `src/lib/room-booking-reconcile.ts:207-215` (คอมเมนต์เล่าบั๊กตัวเอง) ·
`src/lib/room-booking.ts:116-141` (`resolveShootWindow` = กฎช่วงเวลาที่เดียว) ·
`src/lib/__tests__/compose-env-coverage.test.ts:140-152` (skip แบบมีเสียง)

## 7. `the flag nobody reads` — ธงที่ถูกตั้งแต่ไม่มี code path ไหนอ่าน

เพราะมันนับ **แถวใน DB** ไม่ใช่แถวในชีท · `google-sheets.ts` ไม่มี retry และ
**ไม่มี reconciler เดินเก็บของที่หลุด** หลุดแล้วหลุดเลย

รูปทรงของมัน: *ค่าที่ endpoint คืนกลับมาวัดสิ่งที่ await เท่านั้น* ผลข้างเคียงที่
fire-and-forget อยู่นอกสายตาของทั้ง success และ error path พร้อมกัน

**วิธีจับ:** อย่าอ่าน `created` — อ่านของจริงฝั่งปลายทาง
```sql
SELECT count(*) total, count("sheetRowIndex") on_sheet
FROM bookings WHERE "routineGroupId"='…' AND "deletedAt" IS NULL;
```
ตัวเลขไม่ตรง = หลุด · ค้างนิ่งหลายนาที = ไม่ได้กำลังทยอย แต่ตายแล้ว

**ทำแทน:** งานเป็นก้อนให้เว้นระยะ (≥60 วินาที/ก้อน) และ **เช็กปลายทางก่อนยิงก้อนถัดไป** ·
กู้ด้วย `POST /api/admin/backfill-bookings-sheet {apply:true}` (dry-run ก่อนเสมอ —
มันกวาดทุกใบที่ไม่มีแถว ไม่ใช่แค่ของก้อนล่าสุด) · และอย่า restart คอนเทนเนอร์
ระหว่างที่ผลข้างเคียงยังทยอยวิ่ง — ที่ค้างอยู่ใน event loop หายพร้อม process

## Checklist ก่อน merge

ไล่เฉพาะข้อที่ diff ของคุณแตะ:

1. **แจ้งเตือน** — บันทึกผลจริงต่อ channel หรือบันทึกแค่เจตนา? มี endpoint ที่ตอบว่า *คนได้ยินไหม* แยกจาก *worker วิ่งไหม* หรือยัง? (1, 11)
2. **fetch ฝั่ง client** — ถ้าพลาด ผู้ใช้เห็นหน้าตาเดียวกับ "ไม่มีข้อมูล" ไหม? ปุ่มหายไปด้วยหรือเปล่า? (2)
3. **การลบ / การล้าง** — "ไม่เจอ" ของคุณแยก *ไม่มี* ออกจาก *อ่านไม่ได้* หรือยัง? ลบแล้วกู้ได้ไหม? (3, 15)
4. **query ที่มี `take:`** — ลำดับคงที่ไหม ถ้าคงที่ = ท้ายคิวไม่มีวันถึง มีใครอ่านธง truncated? (4, 7)
5. **dry-run** — เดินเส้นเดียวกับของจริงทุกบรรทัดไหม (โดยเฉพาะ guard ที่อยู่ลึกในฟังก์ชันที่ dry-run ไม่เรียก)? (5)
6. **ตัวตรวจ** — success condition ของมันเป็นไปได้ที่จะ *ไม่* เกิดไหม? มันเทียบกับของจริงฝั่งนอกหรือเทียบกับตัวเอง? (6)
7. **กฎใหม่** — กฎนี้มีสำเนาที่อื่นอีกไหม (`grep` ชื่อฟังก์ชัน/ค่าคงที่)? ถ้ามี รวมเป็นที่เดียวก่อน (9)
8. **สิทธิ์** — server อนุญาต → ปุ่มโผล่ → แถวอยู่ในลิสต์ที่เขาเห็น ครบสามชั้นไหม พิสูจน์ด้วย SQL ไม่ใช่ด้วยตาแอดมิน (10)
9. **env ใหม่** — ประกาศใน compose แล้ว (เทส `compose-env-coverage` จับ) · empty string ถูกอ่านเป็น unset ไหม (8)
10. **worker ใหม่** — มี heartbeat key, มีสเปก, และล้มแล้วมีเสียงไหม (11) · **หน้าใหม่** — อยู่ใน `TRACKED_PATHS` และมีเมนูพาไปไหม (13)
11. **log/audit ใหม่ที่ผูกกับ booking** — ใครอ่านได้บ้าง? default ต้อง fail-closed (14)
12. **ผลข้างเคียงที่ไม่ await** (`.then().catch(()=>{})`) — ค่าที่ตอบกลับนับมันด้วยไหม? ถ้าไม่ มีวิธีอ่านของจริงฝั่งปลายทางหรือยัง? (16)
